# V0.7 实机操作：蓝牙主动发现与离线重放

H5、H6 由设备所有者在树莓派上执行。目前状态为**待实机验证**。以下命令适用于已安装 V0.6 Kismet 的 Ubuntu ARM64 设备，在更新为 V0.7 后执行。

## 安装本地控制服务

已按 [V0.7 更新步骤](v0.7-sources.md#从-v06-更新) 安装控制服务的设备，可以直接从 H5 开始。

在 V0.7 源码根目录执行以下命令。安装脚本部署固定的操作入口、文件目录、权限组和 systemd 单元。蓝牙扫描需由操作者每次启动，文件重放需在本机单独授权。扫码、热点和 BLE 校时继续使用现有服务。

```bash
sudo python3 raspberry/config/kismet/configure_sources.py
# V0.7 MCP 模块复制到现有安装目录之后执行
sudo systemctl restart piagent-kismet piagent-mcp
```

## H5　验证内置蓝牙与 BLE 校时共存

1. 在有线终端确认 `hci0` 是准备测试的内置控制器。手机保持连接树莓派热点。在 App 的「蓝牙校时」先做一次校时，记录结果。

   ```bash
   bluetoothctl list
   bluetoothctl show
   sudo btmgmt --index 0 info
   command -v kismet_cap_linux_bluetooth
   ```

   如果最后一条没有输出，使用**与目标机系统、架构和 Kismet 核心版匹配**的软件源安装 `kismet-capture-linux-bluetooth`。BlueZ 的 `bluetoothctl` 和 `btmgmt` 也需要可用。无网树莓派可先在电脑下载相应发行版的签名软件包与依赖，再按 V0.6 的离线安装流程传入。[Kismet 安装包](https://www.kismetwireless.net/packages/)

   ```bash
   # 已配置匹配的官方软件源且可联网时使用
   kismet_version=$(dpkg-query -W -f='${Version}' kismet-core)
   sudo apt-get install --no-install-recommends "kismet-capture-linux-bluetooth=$kismet_version"
   ```

2. 附近放一台已授权用于测试、正在广播的 BLE 设备，或将测试用经典蓝牙设备设为可发现。保持 BLE 校时服务运行，明确同意本次共存试验后执行：

   ```bash
   sudo systemctl start piagent-bluetooth-scan.service
   systemctl status --no-pager piagent-bluetooth-scan.service
   ```

   该单元在控制器已上电、LE 与 BR/EDR 已开启、BlueZ discovery 空闲时才启动。它使用 `linuxbluetooth` 助手，经本机 WebSocket 的限时 `datasource` 凭据上报，附加设备探测关闭。一次运行上限为 120 秒。Kismet 的外部管理端口仍然仅监听回环地址。[Linux Bluetooth 数据源](https://www.kismetwireless.net/docs/readme/datasources_bluetooth/) · [WebSocket 数据源认证](https://www.kismetwireless.net/docs/readme/remotecap/remotecap/)

3. 在这 120 秒内，用手机刷新设备能力，打开 Wireless 的 **Bluetooth Devices**。可用时应显示 **Active Scan**。通过 `get_bluetooth_devices` 查看当前蓝牙源实际发现的设备，从返回结果复制 `id` 给 `get_bluetooth_device_details`。名称、RSSI 和广播服务 UUID 以 Kismet 实际提供为准。观察到其他来源也上报同一设备时，服务仅采用可归属本源的信号。打开「蓝牙校时」再次校时并记录手机结果。

4. 随时停止本次蓝牙扫描。若手机的 BLE 连接或校时受到影响，立即执行停止命令，再记录共存冲突。保留该标记时设备能力显示 `DEGRADED` 及原因。

   ```bash
   sudo systemctl stop piagent-bluetooth-scan.service
   # 仅在实际观察到共存冲突时执行
   sudo install -m 0644 /dev/null /etc/piagent-sources/bluetooth-conflict
   ```

   有线终端可用 `journalctl -u piagent-bluetooth-scan -b --no-pager` 核对本次启动结果。回报控制器型号、是否观察到真实设备、扫描前后校时结果和失败原因。RSSI 缺失应记录为未知。

## H6　重放已有的公开实验文件

1. 准备一份有权使用的真实 PCAP 或 PCAPNG。要验证 AP 或无线设备记录，文件须包含 Kismet 可识别的无线链路层数据。另可使用包含数据包或记录的 KismetDB。通过现有有线文件传输把文件放到树莓派上的临时位置，再由管理员导入专用目录。将示例的文件名和扩展名按实际类型替换。

   ```bash
   sudo install -o root -g piagent-captures -m 0640 "$HOME/lab.pcapng" /var/lib/piagent-captures/lab.pcapng
   command -v kismet_cap_pcapfile
   command -v kismet_cap_kismetdb
   sudo install -m 0600 /dev/null /etc/piagent-sources/allow-replay
   ```

   该目录最多 64 个文件，每个文件最多 64 MiB。仅接受专用目录内的常规文件，文件名使用 ASCII 字母、数字、点、短横线和下划线，首字符为字母或数字。校验会核对实际文件头、KismetDB 表结构、所有者和权限，并拒绝软链接、硬链接及路径参数。[PCAP 数据源](https://www.kismetwireless.net/docs/readme/datasources_pcapfile/) · [KismetDB 数据源](https://www.kismetwireless.net/docs/readme/datasources_kismetdb/)

2. 手机 Captures 页应能看到文件、格式、大小和修改时间。可调用只读的 `list_captures`、`get_capture_metadata(capture_id)`。在树莓派执行下面的命令明确启动一次重放：

   ```bash
   cd /usr/local/lib/piagent-sources
   sudo /usr/bin/python3 -m raspberry.mcp_server.source_control start lab.pcapng --confirm
   sudo /usr/bin/python3 -m raspberry.mcp_server.source_control status
   ```

   从已认证的 MCP 操作端也可调用 `replay_capture`，参数为 `{"capture_id":"lab.pcapng","confirm":true}`。MCP 的模型工具集合只包含可用只读查询。控制端允许同时一个文件、以每秒 50 条记录在 Kismet 内部重放。每次最长 10 分钟，文件不会发回无线网络。

3. 刷新 Captures 页或在 App 通过 `get_capture_status` 核对 `filename`、`state`、数据源 UUID 和本次文件源看到的设备。短文件可以直接进入 `completed`。状态消息说明 Kismet 读到文件末尾后，控制器已关闭文件源；`stopped` 表示手动停止或到达时间上限。格式错误、读取失败和缺少助手会返回明确原因。记录真实设备数量及所用文件类型，小型样本可能没有可识别设备。

4. 若要提前结束正在进行的重放，执行：

   ```bash
   sudo /usr/bin/python3 -m raspberry.mcp_server.source_control stop --confirm
   sudo /usr/bin/python3 -m raspberry.mcp_server.source_control status
   ```

   也可显式调用 `stop_capture_replay`，参数为 `{"confirm":true}`。回报文件格式与大小、状态变化、数据源 UUID、真实设备记录和停止结果。测试后需要关闭后续重放权限时，由管理员移除 `/etc/piagent-sources/allow-replay`。
