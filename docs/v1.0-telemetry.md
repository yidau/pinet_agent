# PocketNet V1 telemetry and message transport

PocketNet uses one native C++ service as the Raspberry Pi business endpoint. The service samples Linux metrics, reads Kismet metadata from loopback, stores bounded events, and serves a TLS gRPC/Protobuf stream on the management hotspot at TCP 9443.

## Runtime responsibilities

- Linux CPU, memory, temperature, frequency, disk I/O and PSI are collected by C++.
- Kismet remains the only raw wireless capture engine. Its managed Linux Wi-Fi source is configured with `filter_mgmt=true`; this retains 802.11 management frames and EAPOL while filtering ordinary data frames.
- A small Python wireless manager is retained only to identify the assigned USB monitor adapter and manage its Kismet datasource. It is not an MCP server and does not expose a phone-facing business API.
- BLE enrollment and BLE time synchronization remain separate Python services.
- The phone subscribes to `TelemetryService.Subscribe`. Snapshots are sent every three seconds. Recent events replay from a FIFO RAM buffer capped at 4096 events and 16 MiB of serialized payload. Individual events are limited to 60 KiB.
- The phone stores event history and its durable replay cursor in SQLite.
- The wire field `boot_id` carries an opaque replay epoch consisting of the Linux boot ID and a process-specific random identifier. Each epoch starts with sequence 1. A stale or out-of-range cursor receives `cursor_reset`. Evicted or rejected sequence ranges receive `history_pruned`. The phone preserves already-synced history across both service and system restarts.
- There is no Raspberry Pi MCP endpoint or Agent runtime.

## Enrollment and transport

The BLE enrollment response contains:

- Pi identity and CA certificate;
- phone identity and bearer token;
- per-phone hotspot SSID and PSK;
- `telemetry_url`, an HTTPS URL whose authority is the gRPC host and whose port is 9443.

The phone uses the CA from the enrollment profile for TLS and sends the bearer token in gRPC metadata. The server checks the existing enrolled-device registry and revalidates authorization while the stream remains open.

## Kismet

Kismet runs continuously with its working directory and home under `/run/piagent-kismet`. Its administrator settings and API token database remain in `/var/lib/piagent-kismet/.kismet`, with readonly and monitor credentials under `/etc/piagent-kismet`. Kismet runs with logging disabled. The dedicated USB source is bound by USB VID/PID, physical USB port, driver and a stable datasource UUID.

The managed source definition includes:

```text
pn-wifi0:type=linuxwifi,name=PiAgent USB monitor,uuid=<fixed UUID>,vif=pn-wifi0mon,retry=false,filter_mgmt=true
```

The filter is a capture policy, not a claim that the hardware stops receiving all other frames. PPS describes packets retained by the configured capture path, not total WLAN throughput. Data-frame-dependent statistics are unavailable in this mode.

## Build and install C++ telemetry

Build on a matching Ubuntu 22.04 ARM64 environment or use a compatible cross-build toolchain. Do not copy a binary built against newer glibc from Ubuntu 26.04.

```bash
sudo apt-get install cmake make g++ pkg-config protobuf-compiler protobuf-compiler-grpc \
  libprotobuf-dev libgrpc++-dev libssl-dev libsqlite3-dev libcurl4-openssl-dev nlohmann-json3-dev
cmake -S raspberry/telemetry -B /tmp/piagent-telemetry-build -DCMAKE_BUILD_TYPE=Release -DBUILD_TESTING=ON
cmake --build /tmp/piagent-telemetry-build --parallel 2
ctest --test-dir /tmp/piagent-telemetry-build --output-on-failure
sudo cmake --install /tmp/piagent-telemetry-build
sudo install -m 0644 raspberry/telemetry/piagent-telemetry.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now piagent-telemetry.service
```

The telemetry service reads the Kismet readonly credential from `/etc/piagent-kismet/client.env`, and uses the existing device registry and TLS server certificate. It does not require a Python MCP service.

## Validation

- Check the telemetry service and Kismet service are active.
- Confirm the gRPC listener is bound only to the management hotspot address.
- Confirm a newly enrolled phone receives a snapshot and can store events.
- Disconnect the phone; collection and event storage must continue.
- Reconnect; the phone resumes from its durable cursor.
- Remove the USB monitor adapter; the hotspot remains available and capture health becomes degraded.
- Reinsert the configured adapter; the datasource manager restores the assigned source.

Actual Monitor Mode, USB driver, filtering behaviour and Raspberry Pi 4B 2GB load must be validated on the user's physical device.
